# Accessibility

## 1. Purpose

This document defines accessibility requirements, implementation principles, and validation criteria for My Portfolio.

The goal is to make the portfolio usable by people with different abilities, input methods, assistive technologies, languages, and display preferences.

Accessibility applies to every public page and interaction, including:

- Homepage and primary navigation.
- Project listings, search, and filters.
- Project detail pages and case studies.
- Public project collections.
- Language and theme switching.
- Error, empty, and not-found states.

## 2. Accessibility Standard

### 2.1 Target Conformance

The project targets **Web Content Accessibility Guidelines (WCAG) 2.2, Level AA**.

Reference: https://www.w3.org/TR/WCAG22/

The implementation should address the four WCAG principles:

1. **Perceivable:** Information and interface elements must be presentable in ways users can perceive.
2. **Operable:** Interface elements must be operable through supported input methods.
3. **Understandable:** Content and interactions must be predictable and understandable.
4. **Robust:** Content must work with browsers and assistive technologies using appropriate standards.

This target does not establish conformance automatically. Conformance must be evaluated against the applicable WCAG success criteria after implementation.

### 2.2 Scope

Accessibility requirements apply to:

- HTML generated by Astro.
- Shared layout and reusable components.
- Client-side search and filtering.
- Theme and language controls.
- Images, diagrams, code examples, and embedded media.
- Third-party embeds and external content where the project controls their integration.
- Responsive behavior at supported viewport sizes.

Third-party services may introduce limitations outside the project's direct control. Such limitations must be identified and documented rather than ignored.

## 3. Semantic HTML and Document Structure

### 3.1 Page Landmarks

Pages should use appropriate semantic landmarks:

- `header` for introductory or site-header content.
- `nav` for navigation regions.
- `main` for the primary page content.
- `footer` for footer content.
- `aside` for complementary content when appropriate.

Each page must have a clear primary content region.

Navigation landmarks should have accessible names when multiple navigation regions need to be distinguished.

### 3.2 Heading Hierarchy

- Use semantic headings in a logical order.
- Give each page a clear primary heading.
- Use lower-level headings to represent actual content hierarchy.
- Do not select heading elements solely for their default visual size.
- Avoid skipped heading levels when they would make the document structure confusing.

Project details and case studies should use headings to organize technical explanations, results, and other substantial sections.

### 3.3 Lists and Relationships

Use semantic lists for collections of projects, navigation items, and related content when appropriate.

Information such as project technologies, metadata, and filter options should have a meaningful structure in the document, not depend exclusively on visual positioning.

### 3.4 Links and Buttons

- Use anchors for navigation to URLs.
- Use buttons for actions that change interface state.
- Do not use non-interactive elements as substitutes for buttons or links.
- Avoid nested interactive elements.
- Ensure each interactive element has a meaningful accessible name.

## 4. Keyboard Accessibility

### 4.1 General Requirements

All functionality must be available using a keyboard unless the underlying task inherently requires a different input method.

Users must be able to:

- Navigate through interactive elements.
- Activate links and buttons.
- Operate the mobile navigation.
- Use search and filters.
- Switch themes and languages.
- Dismiss overlays or expanded panels.
- Return to the expected interaction context after closing a panel.

### 4.2 Focus Visibility

- Provide a visible focus indicator for interactive elements.
- Do not remove the browser's default focus outline without providing an adequate replacement.
- Ensure focus indicators are distinguishable against both light and dark backgrounds.
- Avoid clipping focus indicators with overflow containers.
- Ensure focused controls are not obscured by overlays or sticky content.

### 4.3 Focus Order

Focus order should follow the logical reading and interaction order.

It must not jump unpredictably between distant regions of the page.

Do not use positive `tabindex` values to create an artificial navigation order.

### 4.4 Keyboard Traps

Users must not become trapped in a component without a supported way to exit.

If a modal or other component intentionally manages focus, it must follow the applicable interaction pattern and restore focus appropriately when dismissed.

## 5. Skip Navigation and Page Navigation

### 5.1 Skip Link

Provide a skip link that allows keyboard users to bypass repeated navigation and move to the main content.

Requirements:

- The link must become visible when focused.
- Its destination must exist on the page.
- The destination must be identifiable and focusable where necessary.
- The link must work in both Arabic RTL and English LTR.

### 5.2 Current Page

The current navigation item should be identifiable visually and programmatically.

Use appropriate semantic state, such as `aria-current="page"`, where applicable.

Do not rely on color alone to indicate the active page.

### 5.3 Mobile Navigation

If a collapsible mobile menu is implemented:

- Use a real button to control the menu.
- Expose its expanded state with `aria-expanded`.
- Associate the control with the relevant menu where appropriate.
- Provide a meaningful accessible name.
- Support keyboard activation.
- Keep focus behavior predictable.
- Ensure menu items remain readable at increased text sizes.
- Avoid trapping focus in a non-modal menu.

If the menu is modal, follow the appropriate modal-dialog interaction requirements instead.

## 6. Language and Bidirectional Text

### 6.1 Document Language

Set the document language correctly using the HTML `lang` attribute.

Examples:

- English pages: `lang="en"`.
- Arabic pages: `lang="ar"`.

The value must reflect the actual page language.

### 6.2 Text Direction

Set the appropriate document direction:

- Arabic: `dir="rtl"`.
- English: `dir="ltr"`.

Use CSS logical properties where practical to avoid hard-coded left/right assumptions.

### 6.3 Mixed-Direction Content

Portfolio content may contain Arabic, English, URLs, code, technology names, and identifiers in the same document.

Requirements:

- Ensure mixed-direction text remains readable.
- Isolate bidirectional text where necessary using suitable HTML semantics such as `bdi` or appropriate directionality attributes.
- Preserve code order and punctuation.
- Avoid applying RTL direction blindly to technical code blocks or URLs.
- Test numbers, parentheses, punctuation, and inline Latin text within Arabic paragraphs.

### 6.4 Language Switching

- The language switcher must have an accessible name.
- Available language choices must be understandable.
- The selected language must be identifiable.
- Changing language must update the document language and direction.
- The destination must be valid under the approved routing strategy.
- If the equivalent translation is unavailable, follow a documented fallback behavior rather than silently opening an unrelated page.

The fallback behavior remains an open product decision.

## 7. Color, Contrast, and Themes

### 7.1 Contrast Requirements

The monochrome visual direction does not remove contrast requirements.

Target the following WCAG 2.2 AA minimums:

| Element | Minimum contrast ratio |
|---|---:|
| Normal text | 4.5:1 |
| Large text | 3:1 |
| Essential UI components and graphical objects | 3:1 against adjacent colors, where required |

Large text generally means at least 24 CSS pixels at normal weight, or approximately 18.66 CSS pixels when bold, subject to the WCAG definition.

Logos and other content covered by specific WCAG exceptions must be evaluated according to the relevant criterion.

### 7.2 Light Theme

- Use text colors that remain readable against the selected background.
- Ensure muted metadata remains sufficiently legible.
- Test borders, dividers, controls, and focus indicators.
- Do not assume that a light gray is accessible merely because the design is monochrome.

### 7.3 Dark Theme

- Verify text contrast independently from the light theme.
- Ensure subtle borders remain distinguishable when they convey component boundaries.
- Avoid using extremely low-contrast gray for essential text.
- Check code blocks, disabled states, and focus indicators.
- Verify project images and logos do not disappear against dark surfaces.

### 7.4 Theme Switching

- The theme control must expose its purpose and current state accessibly.
- Switching themes must not make focused elements difficult to see.
- The transition must not introduce unnecessary motion.
- Theme state must be applied consistently to shared components and page content.

### 7.5 Color-Independent Meaning

Never communicate an essential state using color alone.

Examples include:

- Active navigation.
- Selected filters.
- Invalid form fields.
- Disabled controls.
- Current theme or language.
- Search results and errors.

Use labels, icons with accessible names where appropriate, borders, or other supplementary indicators.

## 8. Typography, Zoom, and Reflow

### 8.1 Text Readability

- Use readable type sizes and line heights.
- Avoid long passages with excessively narrow line spacing.
- Preserve clear visual hierarchy.
- Do not use images of text when ordinary text can achieve the same result.

### 8.2 Text Resizing

Text must remain usable when users increase text size.

Avoid fixed heights and overflow rules that clip enlarged content.

### 8.3 Browser Zoom and Reflow

Test layouts at:

- 200% text resizing or equivalent browser text enlargement where applicable.
- 400% browser zoom at a viewport equivalent to 320 CSS pixels wide, as required by the applicable WCAG reflow criterion.

At narrow effective viewport widths:

- Content should reflow into a single-column layout where appropriate.
- Navigation and controls should remain accessible.
- Text should not overlap or become clipped.
- Users should not need to scroll horizontally to read ordinary page content.

Two-dimensional content such as certain data tables and code blocks may require localized horizontal scrolling when permitted by the applicable WCAG criteria.

## 9. Images, Icons, and Media

### 9.1 Informative Images

Provide alternative text that communicates the relevant information or purpose of the image.

For project screenshots, describe the meaningful interface or result rather than using generic descriptions such as "image."

### 9.2 Decorative Images

Use empty alternative text for decorative images so assistive technology can ignore them.

Do not provide redundant alternative text when adjacent content already conveys the same information.

### 9.3 Complex Images and Diagrams

For diagrams or visualizations that communicate substantial information:

- Provide a concise alternative description.
- Include a nearby text explanation or equivalent representation when the information cannot be conveyed adequately in a short description.
- Do not make essential project information available only through a visual diagram.

### 9.4 Icons

- Prefer icons accompanied by visible text when the meaning might be ambiguous.
- Icon-only controls must have accessible names.
- Decorative icons should not create redundant announcements.
- Avoid relying on the shape or color of an icon alone when its meaning is not obvious.

### 9.5 Video and Audio

If video or audio content is added:

- Provide captions for prerecorded video with meaningful audio.
- Provide audio descriptions or equivalent alternatives when needed to communicate essential visual information.
- Provide transcripts for audio content where appropriate.
- Ensure media controls are keyboard accessible.

Media accessibility must be assessed based on the content and applicable WCAG criteria.

## 10. Search and Filtering

### 10.1 Search Input

- Provide a programmatic label.
- Ensure the field is keyboard accessible.
- Make its purpose clear without relying only on placeholder text.
- Keep focus visible.
- Ensure clear actions are accessible when present.

### 10.2 Filter Controls

- Use native form controls where appropriate.
- Associate each control with a meaningful label.
- Group related options semantically when needed.
- Communicate selected states programmatically.
- Provide a way to clear active filters.
- Ensure controls remain usable with keyboard and touch input.

### 10.3 Result Updates

If filtering occurs without a full page navigation:

- Keep keyboard focus predictable.
- Communicate important result changes to assistive technology without excessive announcements.
- Use an appropriate live region for concise updates when needed.
- Avoid moving focus automatically after every filter change unless the interaction pattern requires it.
- Ensure updated results are actually reflected in the rendered interface.

### 10.4 Empty Results

When no projects match:

- Explain that no results were found.
- Provide a clear recovery action.
- Ensure the message is available to assistive technology.
- Avoid repeatedly announcing the same message on every minor interaction.

## 11. Project Cards and Detail Pages

### 11.1 Project Cards

- Use semantic links for navigation.
- Ensure the accessible name identifies the project or destination.
- Avoid duplicate links with confusingly identical names when their destinations differ.
- Do not hide essential information behind hover.
- Ensure focus is visible around the interactive element.

### 11.2 Project Metadata

Use appropriate semantic structures for metadata.

Where a term and value relationship is important, consider a description list.

Do not rely on visual alignment alone to communicate which value belongs to which label.

### 11.3 Technical Content

- Use `pre` and `code` appropriately for code examples.
- Preserve code whitespace.
- Allow localized horizontal scrolling for long code blocks.
- Keep the scrollable area keyboard accessible when necessary.
- Ensure code and syntax highlighting remain readable in both themes.
- Do not communicate syntax meaning solely through color.

### 11.4 Related Projects

Related-project links must have meaningful names.

If several cards use identical visible action text, ensure their link names provide enough context to distinguish the destinations when necessary.

## 12. Public Collections and Error States

### 12.1 Public Collections

- Identify the collection with a meaningful page heading.
- Preserve semantic structure for the project list.
- Make the full-portfolio link accessible.
- Keep collection content usable in both languages and themes.
- Ensure invalid or missing content does not produce confusing broken interactions.

### 12.2 Not Found Page

The not-found page must:

- Communicate the situation clearly.
- Provide a useful navigation path.
- Use the correct document language and direction.
- Preserve the standard keyboard and focus behavior.

### 12.3 Error Messages

- Explain errors in understandable language.
- Associate input errors with the relevant controls when applicable.
- Identify errors without relying only on color.
- Avoid exposing stack traces or internal implementation details.
- Keep recovery actions keyboard accessible.

## 13. Motion and Interaction Preferences

### 13.1 Motion

- Respect `prefers-reduced-motion`.
- Avoid unnecessary parallax, looping animation, and large decorative transitions.
- Do not make animation essential to understanding the interface.
- Ensure animation does not prevent interaction or reading.
- Keep transitions short and restrained when motion is appropriate.

### 13.2 Hover and Pointer Interaction

- Do not make essential information available only on hover.
- Provide equivalent behavior for keyboard and touch users.
- Ensure pointer interactions do not conflict with scrolling.
- Avoid requiring precise pointer movements for essential controls.

### 13.3 Target Size and Spacing

Aim for touch targets of approximately 44 × 44 CSS pixels where practical.

WCAG 2.2 AA includes a specific minimum target-size criterion with defined exceptions; the implementation must be evaluated against that criterion rather than treating the 44 × 44 recommendation as the exact WCAG threshold.

Provide enough spacing between neighboring controls to reduce accidental activation.

## 14. Forms and Inputs

If contact forms or other forms are introduced:

- Every input must have a visible or otherwise programmatically associated label.
- Required fields must be identified accessibly.
- Validation errors must be specific and associated with the relevant fields.
- Preserve entered values when appropriate after validation failures.
- Provide a clear way to correct errors.
- Do not use placeholder text as the sole label.
- Ensure submission feedback is available to assistive technology.
- Avoid resetting the form unexpectedly.

The inclusion of a contact form is not currently a confirmed requirement. These rules apply if one is implemented.

## 15. Astro Implementation Guidance

- Prefer semantic HTML in Astro components.
- Keep static content accessible in the generated HTML.
- Use client-side JavaScript only when needed for interactions.
- Ensure interactive components expose their state and accessible names.
- Do not assume that an accessible component library guarantees accessible composition.
- Test the rendered production output, not only component source code.
- Validate every language-specific layout.
- Avoid introducing hydration solely for static visual behavior.

Accessibility should be incorporated into reusable components rather than added as a final styling pass.

## 16. Testing Strategy

### 16.1 Automated Checks

Use automated tools to identify issues such as:

- Missing accessible names.
- Invalid ARIA usage.
- Some contrast failures.
- Invalid or problematic document structure.
- Certain keyboard and form accessibility problems.

Potential tools include:

- axe-core.
- Lighthouse accessibility audits.
- Browser developer tools.
- HTML validation tools.

Automated results are useful but do not establish WCAG conformance by themselves.

### 16.2 Manual Keyboard Testing

Verify that users can:

- Navigate from the start of the page to the end using a keyboard.
- Reach and activate all controls.
- See focus at every step.
- Operate search, filters, navigation, and theme/language controls.
- Escape from expanded panels and overlays.
- Return to a predictable focus location after closing a component.

### 16.3 Screen Reader Testing

Test representative pages with screen readers and browsers that are appropriate for the supported audience.

Verify:

- Page language and direction.
- Landmark navigation.
- Heading structure.
- Link and button names.
- Form labels and error associations.
- Search and filter updates.
- Expanded and collapsed states.
- Alternative text for informative images.

### 16.4 Visual and Responsive Testing

Test:

- Light and dark themes.
- Arabic RTL and English LTR.
- Mobile, tablet, and desktop widths.
- Browser zoom and enlarged text.
- Focus indicators and contrast.
- Long titles, technical identifiers, and translated labels.
- Empty states, error states, and missing optional content.

### 16.5 Release Gate

A release should not be considered accessibility-validated until:

- No known critical keyboard blockers remain.
- Core flows work without a mouse.
- Applicable contrast requirements have been checked.
- Language and direction are correct.
- Automated checks have been reviewed.
- Manual checks have covered the core user journeys.
- Known limitations have been documented with remediation plans.

## 17. Accessibility Acceptance Criteria

### AC-ACC-001: Semantic Structure

Every public page exposes a meaningful heading hierarchy and primary content region.

### AC-ACC-002: Keyboard Access

All core navigation and interaction flows can be completed using a keyboard.

### AC-ACC-003: Focus Visibility

Interactive elements provide visible focus indicators in both themes.

### AC-ACC-004: Language and Direction

Arabic pages use correct language and RTL direction, while English pages use correct language and LTR direction.

### AC-ACC-005: Contrast

Text and interface elements meet applicable WCAG 2.2 AA contrast requirements.

### AC-ACC-006: Responsive Reflow

Ordinary content remains usable without unintended horizontal page scrolling at the required narrow effective viewport width.

### AC-ACC-007: Accessible Controls

Search, filters, theme switching, and language switching expose meaningful names and states.

### AC-ACC-008: Image Alternatives

Informative images have appropriate alternatives, and decorative images do not create unnecessary announcements.

### AC-ACC-009: Reduced Motion

Nonessential motion respects the user's reduced-motion preference.

### AC-ACC-010: Error Recovery

Error and empty states communicate the problem and provide an appropriate recovery path when possible.

### AC-ACC-011: Assistive Technology

Core flows are manually evaluated with representative assistive technology, in addition to automated checks.

## 18. Open Decisions

The following items remain open:

1. Which browsers and assistive-technology combinations will form the formal test matrix.
2. Whether a contact form will be included.
3. Whether a dedicated accessibility statement will be published.
4. The final mobile navigation and filter interaction patterns.
5. The language-switching fallback when a translation is unavailable.
6. Whether any third-party embeds will be introduced and how their accessibility will be assessed.
7. Which automated accessibility checks will run in continuous integration.

These decisions must be resolved before claiming full conformance.

## 19. Definition of Done

Accessibility is part of the definition of done for every user-facing feature.

A feature is ready when:

- Its semantic structure is correct.
- Its keyboard behavior is usable.
- Its accessible names and states are meaningful.
- Its contrast and focus visibility have been checked.
- Its Arabic and English layouts work correctly where applicable.
- Its light and dark themes remain usable.
- Its responsive behavior has been tested.
- Its relevant automated and manual checks have been completed.
- Known limitations have been recorded and prioritized.

The goal is to make accessibility a consistent property of the portfolio, not a separate feature or a final-stage correction.
